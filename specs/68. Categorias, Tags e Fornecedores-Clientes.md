# Spec 68 — Categorias, Tags e Fornecedores/Clientes

## Status: ✅ Done (2026-08-09 — commits 656c154 backend, 230ca8a frontend; migration 5d434d18c0a2)

Primeira spec da trilha **Despesas (Numis)**. Ordem de implementação da trilha: **68 (cadastros) → 69 (cartões/faturas) → 70 (transações) → 72 (contas a pagar/receber) → 73 (ETL Notion cadastro) → 71 (import LLM) → 74 (dashboard despesas) → 75 (meta renda passiva)**; spec 76 (hub Instituições) é transversal. A 72/73 vêm antes da 71 pra que o import histórico já encontre categorias e regras recorrentes cadastradas.

> Convenção de rotas (decidida 2026-08-09, vale pro app todo): **rota canônica em inglês**, label de UI em português, rota PT antiga mantida como `Navigate replace` — padrão que o app já pratica (`/credit-cards`, `/accounts`, `/transactions`).

## Contexto

O lado "Numis" do sistema (despesas) nunca saiu do protótipo. Antes de qualquer Transaction existir, precisamos dos cadastros que ela referencia: categoria (com hierarquia), tags livres e party (fornecedor/cliente). Decisões da entrevista de 2026-08-09:

- Categoria: CRUD com subcategoria (1 nível) + tags livres por transação.
- Party: **opcional** na transação; auto-criada pelo import a partir da descrição (spec 71); consolidação por merge manual.

### `party_alias`

Suporte ao matching do import (spec 71) e ao merge manual:

| coluna | notas |
|---|---|
| id, workspace_id | |
| party_id | FK party |
| alias_normalized | descrição normalizada — único por workspace |

**Helper único de normalização**: `normalize_description()` em `services/normalize.py` (uppercase, remove `*`, remove dígitos/UF finais, colapsa espaços, trim). É o MESMO helper usado pelo fingerprint de dedup da spec 70/71 — duas normalizações divergentes quebrariam o matching.

**Merge de parties** = re-apontar `transaction.party_id`, `party_alias.party_id`, `recurrence_rule.party_id` e `scheduled_transaction.party_id` (spec 72) pro sobrevivente + hard delete do duplicado, tudo numa transação, com audit log. (Merge é a exceção deliberada à regra "referenciada → só desativa": depois do re-apontamento o duplicado não é mais referenciado.)

## Backend

- CRUD REST padrão do repo: `/api/categories`, `/api/tags`, `/api/parties` (list/create/update/deactivate). Workspace-scoped, `role in (admin, sysadmin)` pra escrita, member lê.
- `POST /api/parties/{id}/merge` body `{ source_party_id }` — merge com audit log.
- Validações: categoria com parent não pode virar parent; delete de categoria/party só desativa se referenciada (exceção: merge, acima).

## Frontend

- Página **`/registry`** (label sidebar: **Cadastros**, grupo Caixa & Cartões; redirect PT `/cadastros`) com 3 abas: Categorias, Parties, Tags.
  - Categorias: árvore de 2 níveis, cor, kind, criar/editar/desativar inline.
  - Parties: lista com busca, badge kind, contagem de aliases; ação Merge (seleciona 2 → escolhe sobrevivente).
  - Tags: lista simples, rename, delete se sem uso.
- Modais fecham com ESC (`useEscapeKey`). Ações async com disabled+spinner, erros em toast.

### Deltas declarados vs protótipo

- Página `/registry` **não existe no protótipo** (lá "Cadastros" é só um grupo do dropdown Novo, l.2069-2073) — tela nova, desenhada no padrão visual das demais. A colisão de label com o grupo do dropdown é aceita (ambos significam cadastros).
- Auto-categorização por descrição (`suggestedCat` do proto, l.6120-6132) fica **fora do MVP** — delta declarado; o modelo `party_alias` + categoria já preparam a base pra spec futura.
