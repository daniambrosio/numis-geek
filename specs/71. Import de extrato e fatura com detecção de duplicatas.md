# Spec 71 — Import de extrato e fatura com detecção de duplicatas

## Status: 📝 Draft

Trilha Despesas (ordem de implementação): 68 → 69 → 70 → 72 → 73 → **71** → 74 → 75. Depende de 70 (transaction/fingerprint/pay_invoice), 69 (invoice) e **72/73** (scheduled_transactions e categorias já cadastradas — por isso o import vem depois delas: o histórico já nasce casando com regras e categorias reais). É a **entrada principal de dados** do lado Numis: o user não digita transação — importa arquivo.

## Contexto

Decisões da entrevista (2026-08-09):

- Formatos reais do user: **OFX, PDF (fatura), CSV/XLSX (Wise/Nubank), screenshot**.
- **LLM pra tudo** — reusa o pipeline `ExtractionJob` (specs 38/48/49/58): attachment → job → extracted_json → review UI → apply. Sem parser determinístico por ora (otimização futura se algum formato ficar frequente).
- **Sem histórico do Notion** — o histórico entra por estes arquivos originais das instituições.
- **Dedup em 3 camadas obrigatório desde o dia 1**: os arquivos do user têm períodos sobrepostos.
- Party auto-criada da descrição (match exato via alias — `normalize_description` da spec 68; consolidação manual depois).

## Dedup — 3 camadas

1. **Hash do arquivo**: `attachment.content_hash` (SHA-256, coluna nova via batch_alter + backfill dos existentes). Upload de arquivo com hash já existente no workspace → recusado na hora com mensagem apontando o attachment original.
2. **Fingerprint da tx**: usa a coluna `transaction.fingerprint` definida na spec 70 — computada em **toda** tx (manual ou importada), fórmula sha1(`source_type` + FK da origem + `event_date` + `amount` + `currency` + `normalize_description`). No apply, linha extraída cujo fingerprint já existe na mesma conta/cartão → bucket "duplicada" (default: skip, mostrada no review). Como tx manuais também têm fingerprint, um lançamento digitado antes do import é capturado aqui.
3. **Aviso de overlap de período**: `extraction_job` ganha `statement_period_start/end` (o LLM extrai do documento). Se a faixa intersecta a de um job CONFIRMED anterior da mesma conta/cartão → banner "Overlap com import de DD/MM–DD/MM — N linhas caíram como duplicatas" antes do apply.

Caso legítimo de tx idêntica no mesmo dia (2 cafés de R$ 5): aparece no bucket duplicada e o user pode promover a linha pra "importar mesmo assim" (persiste fingerprint com sufixo `:2`).

## Extensões ao pipeline ExtractionJob

- Novos `ExtractionSourceHint`: `BANK_STATEMENT`, `CARD_INVOICE` — **migration de enum via `op.batch_alter_table`** (SQLite).
- Novos `AttachmentSourceType`: `ACCOUNT` e `CREDIT_CARD_ACCOUNT` (mesma migration) — o attachment do extrato ancora na conta (`source_id` = account.id, NOT NULL como hoje); o da fatura, no cartão.
- `extraction_job` ganha `checking_account_id?` / `credit_card_account_id?` (scoping, análogo ao `institution_id` da spec 58) + `statement_period_start/end`. Jobs desse fluxo não têm snapshot_id.
- Templates de prompt novos em `extraction_templates`:
  - `BANK_STATEMENT`: emite `transactions[] { event_date, description, amount signed, currency, balance_after? }` + `period {start,end}`.
  - `CARD_INVOICE`: emite o de cima + `invoice { close_date, due_date, total, iof_total? }` + por linha `installment "5/12"?`, `fx { usd_amount, rate }?` (compra internacional).
- Classify (novo serviço `_classify_bank_import`):
  - resolve party por `party_alias` (match exato normalizado); sem match → marca "party nova: UBER *TRIP" (criada no apply).
  - calcula fingerprint e bucketiza: **novas / duplicadas / pagamento de fatura detectado / quita agendamento**.
  - **Pagamento de fatura**: linha de extrato que bate com invoice CLOSED não paga (|valor| ±1%, data entre close_date e due_date+10 — matcher específico de fatura, deliberadamente mais estrito que o de AP/AR abaixo) → sugere quitação; ao confirmar, o apply chama o serviço **`pay_invoice` da spec 70** (efeitos idênticos ao botão — nunca escreve PAID/FKs por fora).
  - **Quita agendamento (AP/AR)**: aplica as regras de matching definidas na spec 72 (±5% valor, ±5 dias do due_date, party/descrição; tie-breaker por data mais próxima) contra occurrences PENDING. Match confirmado → occurrence PAID + `paid_by_transaction_id` + tx herda category/party da occurrence se vazios.
  - CARD_INVOICE: resolve/cria a `invoice` pelas datas do documento; seta `total_amount` (positivo), `iof_total` e `status=CLOSED`; linha `X/Y` de parcela vira tx com installment preenchido (o vínculo parent entre parcelas de meses diferentes é best-effort por descrição+valor).
- Apply: cria transactions com `is_reconciled=true`, parties novas + aliases; atômico; auditado.

## UX

- Botão **Importar extrato** na página da conta (`/accounts/:id`, spec 70) e **Importar fatura** no `/credit-cards/:id` (destrava os botões disabled da spec 69). Upload → job async (padrão spec 48: polling, spinner, toast).
- Review modal (padrão `BulkIncomeReviewModal`): tabela com buckets colapsáveis (novas / duplicadas / pagamento de fatura / quita agendamento), edição inline de categoria/party antes do apply, contador "Importar N transações". ESC fecha.
- Timeout: LLM pode levar 1–3 min (proxy já configurado pra 600 s).

## Fora de escopo

- Auto-categorização por LLM (o modelo pode sugerir `category_hint`; aplicar de verdade é spec futura).
- Parser determinístico por formato.
