# Spec 66 — Crypto rewards pagos em cripto (in-kind)

## Status: 📝 Draft

Nota: commit `ba186fc` (prompt BROKER_INCOME v1→v2) é pré-requisito já em produção; esta spec parte do v2.

## Contexto

Coinbase Brasil paga rewards de USDC em **BTC** (`+0.000571 BTC = +R$ 187,72`). O modelo atual de Distribution/AssetMovement trata provento (cash flow, sem qty) e compra (movimento de qty) como coisas separadas. Reward pago in-kind é os **dois ao mesmo tempo**:

- **Provento**: R$ 187,72 de rendimento do USDC (P&L do mês)
- **Aporte**: +0.000571 BTC no saldo do asset BTC (qty)

Modelo atual força o user a subir 2 extratos separados (proventos + posições) pra reconciliar. Spec 66 pede que o LLM extraia crypto rewards como **par acoplado** de eventos que o user revisa e confirma junto.

Precede a spec 65 (parcial deploy 25c7bfd/93c80d2) — MoMDeltaBlock já removido, coluna Δ % inline. Spec 62 SUSPICIOUS_DELTA deprecated (enum preservado).

## Escopo (só crypto rewards)

Rewards de exchange cripto (Coinbase/Binance/etc.) pagos em cripto. Fora:
- DRIP (dividendo pago em ações) — fica pra spec futura se aparecer no portfólio.
- Interest normal (renda fixa, bonds) — já cobertos por Distribution INTEREST simples.

## Comportamento novo

### Prompt LLM (BROKER_INCOME v3)

Bump versão. Detectar padrão "crypto reward pago em cripto":

- Extract linha `USDC rewards +R$ 187,72 +0.000571 BTC`:
  - Emite `events[]` com **UM evento INTEREST**:
    - `ticker_raw`: 'USDC' (cripto que gerou o rendimento)
    - `gross_amount`: 187.72
    - `currency`: 'BRL'
    - `payment_in_kind` (novo campo opcional): `{ ticker: 'BTC', quantity: 0.000571 }`
  - `payment_in_kind` só quando o pagamento vier em cripto diferente do gerador.
  - Se ausente → tratamento normal (INTEREST em cash).

### Backend `_classify_bulk_income`

- Se `event.payment_in_kind` presente:
  - Resolve o cripto pago (`payment_in_kind.ticker`) via `_resolve_asset_by_ticker_or_name` no workspace + FI scope.
  - Se resolver, emite **DOIS rows** no `preview`/`apply_plan`:
    1. **INTEREST** (Distribution) — como antes, ticker_raw=USDC, gross em BRL. `row_kind='distribution'`.
    2. **BUY** (AssetMovement) — asset=BTC, qty=0.000571, gross=187.72, currency=BRL, fx_rate resolved via `resolve_fx_rate(event_date)`. `row_kind='in_kind_receipt'`, `related_external_id`=external_id da Distribution.
  - Se não resolver o cripto pago (asset BTC não existe no workspace/FI) → **orphan** ambos com hint claro; user pode criar o asset e re-subir.
- `external_id` do BUY inclui suffix `:in_kind` pra evitar colisão com BUY normal em mesmo dia.

### Apply

Transação atômica. Cria Distribution + AssetMovement dentro do mesmo `db.commit()`. Se qualquer um falha, ambos rollback. Não persistir só um dos dois.

### Frontend `BulkIncomeReviewModal` — preview em 2 linhas

Rows do LLM que geraram par mostram **2 linhas visualmente pareadas**:

```
2026-07-31  INTEREST      USDC              R$ 187,72
    ↳ recebido em BTC:  BUY      BTC   +0,000571     (aporte de reward)
```

Contador "Registrar N proventos" muda pra "Registrar N eventos" (mistura Distribution + Movement).

Visual: linha 2 com indentação + ícone `↳` + cor mais suave (gray-500), pra deixar claro que é o par da linha acima.

### Cash impact — regra do gross

O BUY BTC tem `gross_amount=R$ 187,72` mas **não representa cash spent**. Semanticamente é "recebi BTC valorado em R$ 187". Não deve reduzir "Saldo em Conta" da corretora. O `compute_position` do BTC vai adicionar qty=0.000571 ao holding. E o `total_invested_brl` do BTC ganha +R$ 187,72 (basis update — importante pra rentabilidade futura).

Se user olhar o "Saldo em Conta (Coinbase)" no snapshot, deve permanecer inalterado por essa operação. Modelo atual funciona porque o extract de posições da Coinbase mostra o Saldo em Conta como está (não afetado por rewards em kind).

## Deliverables

1. **Prompt LLM v3** em `extraction_templates/__init__.py`:
   - Adicionar seção "PAGAMENTO EM KIND (crypto rewards em cripto)"
   - Instrução de emitir `payment_in_kind: { ticker, quantity }` no event
   - Exemplo Coinbase USDC → BTC no prompt

2. **Backend `_classify_bulk_income`**:
   - Detectar `payment_in_kind` no event
   - Resolver asset alvo
   - Emitir 2 rows (INTEREST + BUY) no preview/apply_plan com pareamento via `related_external_id`
   - Apply atômico dentro de transação

3. **Frontend `BulkIncomeReviewModal`**:
   - Reconhecer `row_kind='in_kind_receipt'` no preview
   - Renderizar linha secundária pareada com indentação + ícone
   - Ajustar label do botão pra "Registrar N eventos"

4. **Model**: Distribution `external_id` fica igual. AssetMovement recebe novo external_source variant `MANUAL_CSV_IN_KIND` (ou reuso do MANUAL_CSV com suffix no external_id). Sem migration se optar por suffix.

5. **Testes**:
   - Regression: LLM output com `payment_in_kind` → 2 rows no preview
   - Regression: LLM output sem `payment_in_kind` → 1 row (comportamento antigo)
   - Regression: asset destino não existe → ambos orphan
   - Apply atômico: erro no BUY → Distribution não persiste

## Fora do escopo

- DRIP (spec futura)
- Interest normal (já funciona)
- Split de reward entre múltiplos criptos (raro; ignorar)
- Reward de staking com lock-up (bloquear qty temporariamente) — modelo simples: qty entra imediatamente

## Success

- User sobe 1 print de rewards Coinbase, revisa 5 pares no modal (10 linhas visíveis), clica Registrar
- Sistema cria 5 Distributions + 5 AssetMovements em transação atômica
- Snapshot mensal reflete +qty BTC + P&L rendimento

## Migration

- Sem alteração de schema. `external_id` do BUY usa suffix pra idempotência.
- Se user re-subir o mesmo print, dedup por external_id evita duplicação.
