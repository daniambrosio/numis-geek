# Spec 77 — Holerites (CLT)

## Status: 📝 Draft

Trilha Despesas (ordem de implementação revisada): 68 → 69 → 70 → 72 → 73 → 71 → **77** → 74 → 75.
Depende de **70** (`transaction`), **71** (pipeline de import + `attachment.content_hash`) e **68** (category/party).
Entra **antes da 74** porque a despesa mensal média — a métrica-alvo da trilha — está incompleta sem os descontos em folha.
Emenda as specs **71**, **73**, **74** e **75** (seção própria no fim).

## Contexto

O user é CLT. Hoje o sistema não tem nenhum conceito de renda do trabalho: a única forma de registrar salário seria uma Transaction de categoria "Salário" com o valor **líquido**. Isso perde três coisas que importam:

1. **Descontos em folha que são despesa real** (plano de saúde, odonto, coparticipação, seguro de vida, vale-transporte) nunca aparecem no extrato bancário — logo, a despesa mensal média da spec 74 os subestima silenciosamente.
2. **FGTS** é patrimônio (o repo já tem 3 ativos `AssetClass.FGTS` — Carrefour, Eletrobras, Meli — na mesma conta de investimento) e o depósito mensal não tem hoje nenhuma origem automática.
3. **Bruto, INSS e IRRF** — sem eles não existe alíquota efetiva nem base pra spec 75 responder "que fração do meu salário a carteira já substitui".

### Premissa central: holerite é uma fatura invertida

A spec 69 já modela o padrão: **um documento com N linhas que se liquida em 1 movimento de caixa**. Holerite é o mesmo shape com o sinal trocado. Reusamos a estrutura, não inventamos outra.

### Decisões da entrevista (2026-08-19)

| # | Decisão |
|---|---|
| a | **Detalhe linha-a-linha** — cada rubrica do holerite vira uma linha persistida, não só bruto/descontos/líquido |
| b | **FGTS vira aporte** no ativo `AssetClass.FGTS` do empregador correspondente (os 3 ativos já existem) |
| c | **13º e férias são payslips de tipo diferente** — cada um tem PDF próprio |
| d | **Adiantamento + saldo = 2 créditos** no mês — o modelo suporta 1..N transações por holerite |
| e | **Descontos-despesa entram na despesa média** via `payslip_line.category_id` (sem Transaction sintética) |
| f | **VR/VA é informativo** — linha `INFORMATIONAL`, não vira conta de benefício |
| g | **Import**: empregador atual + histórico que existir em PDF |

```python
class PayslipLineKind(str, enum.Enum):
    EARNING               = "EARNING"                # provento: salário, HE, adicional, DSR, férias
    DEDUCTION             = "DEDUCTION"              # reduz o líquido: INSS, IRRF, plano, adiantamento
    EMPLOYER_CONTRIBUTION = "EMPLOYER_CONTRIBUTION"  # FGTS do mês, INSS patronal — não afeta o líquido
    INFORMATIONAL         = "INFORMATIONAL"          # bases de cálculo, VR/VA, salário família
```

### Invariantes (validação de serviço → 422)

1. `gross_amount == Σ amount WHERE kind = EARNING`
2. `deductions_amount == Σ amount WHERE kind = DEDUCTION`
3. `net_amount == gross_amount − deductions_amount`
4. `EMPLOYER_CONTRIBUTION` e `INFORMATIONAL` **não entram** em nenhuma das três somas
5. `category_id`, quando presente, aponta pra subcategoria (`parent_id IS NOT NULL`)
6. `is_tax` e `is_advance_offset` só em `kind = DEDUCTION`; linha com qualquer um dos dois `true` **não pode** ter `category_id`
7. `installment_number` não-nulo ⇒ `type = THIRTEENTH`

Tolerância de R$ 0,01 nas somas (arredondamento de holerite). Divergência maior é erro editável no review, nunca silenciada.

### Liquidação — `transaction.payslip_id`

Migration desta spec, `op.batch_alter_table` em `transaction`: `payslip_id` FK payslip nullable, indexado.

**Lado autoritativo único, sem espelho na `payslip`.** Diverge deliberadamente da spec 69/70 (onde `invoice.paid_by_transaction_id` é espelho denormalizado): lá o espelho existe porque `pay_invoice` também escreve `status` e `paid_at`; aqui não há estado derivado a manter, então espelho seria dívida gratuita.

Relação **1..N**: um holerite pode ser liquidado por mais de uma transação — cobre o caso (d), adiantamento + saldo, quando o empregador não emite PDF separado.

Derivados em query:

```
settled_amount    = Σ transaction.amount WHERE payslip_id = :id
settlement_status = SETTLED  se |net_amount − settled_amount| ≤ 0,01
                    PARTIAL  se 0 < settled_amount < net_amount
                    UNSETTLED se settled_amount = 0
```

A transação do líquido é uma tx comum da spec 70: `source_type = CHECKING`, `amount` **positivo** = líquido creditado, subcategoria de `kind = INCOME`, `party_id` = empregador.

Serviço `link_payslip_transaction(payslip, transaction)` / `unlink_...`: valida workspace, `source_type = CHECKING`, `amount > 0`, e que a tx não está vinculada a outro holerite. Atômico e auditado (`payslip.link_transaction`).

## Regra de agregação — o gross-up

É a parte que não pode sair errada, e é a razão de a spec 77 vir antes da 74.

**O conflito.** O banco credita o **líquido** — a tx tem que valer o líquido, senão o extrato importado não bate (invariante da spec 71). Mas o plano de saúde de R$ 500 descontado em folha **é despesa**, e nunca vai aparecer em extrato nenhum.

**A regra.** No `/api/expenses/summary` (spec 74), para cada holerite com `competence_month` no mês:

```
renda_do_mês   += payslip.net_amount
                + Σ payslip_line.amount  WHERE kind=DEDUCTION
                                           AND category_id → subcategoria kind=EXPENSE
despesa_do_mês += Σ (as mesmas linhas)
```

Consequências, todas desejadas:

- **Resultado do mês** (renda − despesa) continua exatamente igual ao líquido → bate com o caixa ✅
- **Despesa mensal média** passa a incluir plano de saúde, odonto, seguro de vida, VT ✅
- **INSS e IRRF** (`is_tax = true`) ficam fora dos dois lados — não são despesa discricionária, são renda que nunca chegou. Aparecem só como alíquota efetiva no holerite ✅
- **`is_advance_offset = true`** fica fora dos dois — é timing de caixa ✅
- **`EMPLOYER_CONTRIBUTION` e `INFORMATIONAL`** nunca entram ✅

**Anti-dupla-contagem.** A spec 74 ganha uma exclusão estrutural nova, na mesma família de `paid_invoice_id` e `transfer_group_id`:

> `transaction.payslip_id IS NOT NULL` → a tx sai das somas de renda; a renda daquele mês vem inteira do holerite.

Isso também resolve o histórico retroativo: holerite importado **sem** o extrato correspondente (`UNSETTLED`) ainda conta como renda — o dinheiro entrou, só não temos o arquivo do banco. O risco simétrico (extrato importado e holerite não vinculado → conta duas vezes) é mitigado pelo matcher da Fase 3 e exposto como indicador de qualidade `unlinked_payslips_count`, ao lado do `uncategorized_pct` que a 74 já prevê.

Mês sem holerite cadastrado se comporta como hoje: a renda vem das transações. Retrocompatível.

## FGTS → aporte no ativo

Linha `EMPLOYER_CONTRIBUTION` cuja descrição casa `/fgts/i` (ou marcada manualmente no review) alimenta `payslip.fgts_amount`. No apply, gera um `AssetMovement`:

```python
AssetMovement(
    asset_id      = payslip.fgts_asset_id,
    type          = AssetMovementType.BUY,
    event_date    = payslip.pay_date,
    quantity      = Decimal(1),              # convenção value-mode do repo
    unit_price    = payslip.fgts_amount,     # (migration normalize_modo_valor_qty
    gross_amount  = payslip.fgts_amount,     #  + MovementComposer.tsx ~l.405)
    net_amount    = payslip.fgts_amount,
    currency      = Currency.BRL,
    fx_rate       = resolve_fx_rate(db, payslip.pay_date),
    external_source = ExternalSource.PAYSLIP,
    external_id     = f"payslip:{payslip.id}",
)
```

`AssetClass.FGTS` está fora de `positions._COTADO_CLASSES`, então é **modo valor**: `compute_position` força `effective_qty = 1` e acumula o aporte em `non_cotado_basis_brl`. O valor de mercado (com juros e TR) continua vindo do snapshot mensal. Semântica correta: **aporte vira base, rendimento vira delta de fechamento.**

- **Migration**: `ExternalSource` ganha `PAYSLIP` (`op.batch_alter_table` — SQLite).
- **Idempotência**: o índice parcial `ix_asset_movement_external` já existente garante que reimport não duplica.
- **Resolução do ativo**: `fgts_asset_id` herda do último payslip do mesmo `employer_party_id`; sem histórico, o review modal pede (dropdown filtrado por `asset_class = FGTS`). **Nunca cria ativo automaticamente** — os 3 já existem e a granularidade por empregador é o que torna a resolução determinística.

> ⚠️ **Guarda de snapshot fechado.** Aporte com `event_date` dentro de mês com `portfolio_snapshot.status = CLOSED` **não** recomputa o snapshot (invariante da spec 52). O apply avisa: "N aportes caem em meses já fechados — a base histórica não muda; o degrau aparece no próximo fechamento". Mesmo racional do degrau de PM registrado no `TODO.md`.

### `_classify_payslip`

1. Resolve empregador por `party_alias` (`normalize_description` da spec 68); sem match → "party nova: MERCADOLIVRE BRASIL LTDA" (criada no apply).
2. Checa a unique `(workspace, employer, type, competence, installment)` → bucket **duplicado**.
3. Marca `is_tax` por regex (`inss|irrf|irpf|imposto de renda|previd[êe]ncia`) e `is_advance_offset` (`adiantamento|adto|antecipa`).
4. **Memória de rubrica** — sugere `category_id` buscando a última `payslip_line` do mesmo empregador com a mesma `description` normalizada. Efeito prático: o 1º holerite se categoriza à mão, do 2º em diante vem pronto. Substitui auto-categorização por LLM com zero custo e zero alucinação.
5. Valida as invariantes 1–3; divergência > R$ 0,01 → bucket **divergência de soma** (editável).
6. Resolve `fgts_asset_id` (herda do último payslip do empregador).
7. Buckets: **novo / duplicado / divergência de soma / rubrica nova sem categoria**.

### `_apply_payslip`

Cria `payslip` + linhas + party/alias novos + `AssetMovement` de FGTS. Atômico, auditado, ramo próprio em `_apply_payload`.

**Não cria a Transaction do líquido** — deliberado. A fonte de verdade do caixa é o extrato (invariante da spec 71: "o user não digita transação, importa arquivo"). O vínculo vem do matcher da Fase 3 ou do botão manual. Enquanto não vier, a exclusão estrutural do gross-up já garante que a renda não some.

## Emendas a specs existentes

### Spec 74 — Dashboard de Despesas

1. Exclusão estrutural nova: `transaction.payslip_id IS NOT NULL` sai das somas (a renda vem do holerite).
2. `renda_do_mês += Σ payslip.net_amount + gross-up` (regra acima).
3. `despesa_do_mês += Σ payslip_line` DEDUCTION com categoria de `kind = EXPENSE`.
4. Novo indicador de qualidade ao lado de `uncategorized_pct`: **`unlinked_payslips_count`**.
5. Nova saída no `/api/expenses/summary`: `avg_monthly_work_income_12m`.

### Spec 75 — Meta de renda passiva

1. Novo insumo: `renda_trabalho_mensal_média` (dos holerites, 12 meses fechados).
2. Nova métrica por cenário: **Cobertura da renda de trabalho** = `renda_passiva_mensal / renda_trabalho_mensal` — responde "que fração do meu salário a carteira já substitui", complementar à cobertura de despesa.

### Spec 71 — Import de extrato

`_classify_bank_import` ganha bucket **"vincula holerite"**: crédito em conta checking com `|amount − payslip.net_amount| ≤ 0,01` e `pay_date ± 5 dias` contra payslips `UNSETTLED`. Confirmar aplica o link. Matcher mais estrito que o de AP/AR — o líquido do holerite é um valor exato, não uma estimativa.

### Spec 73 — Import Notion de cadastros

**Pré-requisito da Fase 1**: garantir subcategorias `INCOME` (Salário, 13º, Férias, PLR) e `EXPENSE` de folha (Plano de saúde, Odonto, Seguro de vida, Vale-transporte). Se não vierem do Notion, criar em seed condicional (idempotente) desta spec.
